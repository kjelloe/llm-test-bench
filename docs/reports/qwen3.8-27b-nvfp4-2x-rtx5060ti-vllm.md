# Qwen3.8-27B NVFP4 on 2× RTX 5060 Ti (vLLM, tp=2) — benchmark results

Results from this repo's benchmark, run 2026-09-24, in the `./statistics.sh` output formats so they
can sit next to the llama.cpp rows. The raw runs are bundled beside this file as
`qwen3.8-27b-nvfp4-2x-rtx5060ti-vllm-export.json`; import with

```bash
./statistics.sh --import docs/reports/qwen3.8-27b-nvfp4-2x-rtx5060ti-vllm-export.json
```

after which every `statistics.sh` view includes these rows (files land in `output/` as
`results-import-2x_RTX_5060_Ti_31GB-07ad1fba-*.json`).

## Setup

| | |
|---|---|
| Model | `QUASAR-QAT/Qwen3.8-27B-QUASAR-NVFP4` (HF safetensors, compressed-tensors NVFP4: 4-bit weights **and** 4-bit activations, group 16, fp8 scales; 20.6 GB) |
| Engine | vLLM `0.30.1rc1.dev68+gbbd7c24d6` (main, precompiled wheel), `--tensor-parallel-size 2`, native Anthropic and OpenAI endpoints |
| Kernels | W4A4 NVFP4 CUTLASS GEMM + FlashInfer Gated-DeltaNet prefill on SM12x. Needs vLLM main from 2026-09-08 or later; the 0.29.0 release and older mains run the same model as W4A16 with Triton GDN prefill at half the prefill speed, with no error |
| GPUs | 2× NVIDIA GeForce RTX 5060 Ti 16 GB (Blackwell sm_120), driver 595.91.07, CUDA 13.2. Card 0 PCIe gen5 x8, card 1 gen4 x4 (chipset lanes); no P2P between GeForce cards, so the tp=2 all-reduce goes through host memory |
| Host | AMD Ryzen 7 9800X3D, 92 GB DDR5, NVMe, Ubuntu (Linux 6.8.0-139-generic), bare metal |
| Bench entries | `models/2x16gb.vllm`: `qwen3.8-27b:nvfp4-next` = `tp=2,dtype=auto,max_model_len=32768,language_model_only,max_num_seqs=4,enable_prefix_caching`; `qwen3.8-27b:nvfp4-next-128k` = same with `max_model_len=131072` |
| Serving config | The same weights serve a dev pipeline at `max_model_len` 65,536, `--gpu-memory-utilization 0.92` (139,810 KV tokens on the cards), `--max-num-seqs 8`, plus 32 GiB of CPU KV offload. `max_model_len` only sizes the KV pool, so the pass rates and single-stream tok/s below carry over unchanged |

## Reading the numbers

- **Coding set: 26/28 (92.9%) as recorded; 27/28 (96.4%) as a capability score.** The
  `dotnet_sas` TOOL_ERROR was a missing .NET 9 SDK on this box (the task's own tooling, excluded from
  `skill` by the harness); the third file is its rerun after installing .NET 9, which passed. The
  one real failure is `node_paratrooper` (L6): 1 pass in 7 attempts on this build (a PASS in the
  earlier spot run, 134 s; TESTS_STILL_FAIL in the full run and five reruns, all at temperature 0),
  so treat L6 as borderline rather than a clean fail. Everything from L1 to L5 passes, L6 is 1/2.
- **`python_hashmap` (the precision canary) passes** with 4-bit activations on the W4A4 kernel, so
  NVFP4 W4A4 costs nothing on this task. On the older W4A16 build the same model scored spot 9/10 at
  30.0 tok/s; the new kernels give 10/10 at ~32 tok/s (same weights, same tasks).
- **Single-stream speed: 32-33 tok/s** on every coding task, prompt 0.4k-7.4k tokens, output up to
  4.6k tokens, with no slow-down on the long outputs (`node_para_combat`: 3.9k tokens at 32.6 tok/s).
- **vLLM tok/s is generated tokens over total request time.** vLLM's API has no prefill/decode
  timing split like llama.cpp's, so the harness divides by the whole wall time. For the coding
  tasks (short prompts) that is decode speed. For the context tasks it is not: they emit ~15 tokens
  after a 7k-100k prompt, so the `ctx_*` columns measure prefill. Read them as prompt tokens per
  second instead:

| Task | Prompt tokens | Wall s | Prefill tok/s |
|---|---|---|---|
| context_8k | 7,336 | 4.07 | 1,802 |
| context_16k | 14,392 | 7.51 | 1,916 |
| context_32k | 28,455 | 15.25 | 1,866 |
| context_64k | 56,722 | 33.97 | 1,670 |
| context_128k | 100,534 | 71.1 | 1,414 |

  All context tasks up to 128k pass; `context_256k` is SKIPPED_VRAM (the 131072 entry's KV pool).
  Prefill holds ~1.7-1.9k tok/s to 64k and drops to 1.4k tok/s at 100k tokens. For comparison, the
  older W4A16 + Triton build prefilled at about half that.
- **Concurrency (from the serving side, not this harness):** with real agent transcripts of 24-43k
  tokens, one agent decodes at ~35 tok/s, four agents total ~50 tok/s (~18 each) and eight agents
  still ~51 tok/s total once contexts that fall out of the 140k-token GPU pool are offloaded to CPU
  RAM instead of recomputed. Six real coding tasks solved agentically at once: 6/6 in 130 s.
- **Export header vs table:** the export bundle labels the cards "15GB" / "31GB" (integer division
  of 16,311 MB) where the statistics table rounds to 16 GB / 32 GB; same hardware.
